Two kinds of repo

Knowing which one you’re looking at explains everything else.

create_sprint_branch

Holds the logic. The copyable payload sits under template/, and nothing here is scheduled — this repo never cuts a sprint branch for itself. You come here to change behaviour for everyone.

Your product repos

Each gets its own copy of the workflows plus a .github/sprint.yml. Teams on different cadences share the same tooling without agreeing on a schedule.

The payload is copied, not referenced. A fix made in create_sprint_branch reaches a product repo only when someone re-runs the installer against it — see Rolling out updates.

The pipeline

One hop runs itself. The rest wait for you, because “verified in DIT” is a judgement only a person can make.

Where feature work goes

Point feature pull requests at the sprint branch, not at develop. Everything merged during the sprint ships together when that branch is promoted.

A release is a branch cut from UAT, not a merge — so that last step opens no pull request. It just creates release/<sprint> at whatever UAT currently points to.

Install in a repo

Roughly ten minutes per repo, most of it deciding the cadence.

  1. Run the installer

    Clone the tooling repo once, then point it at any repo you own.

    terminal
    git clone https://github.com/vib795/create_sprint_branch.git
cd create_sprint_branch
./tools/install.sh /path/to/your/repo

    It writes the four workflows, the sprint package and the tests. An existing requirements.txt is appended to, never replaced, and an existing sprint.yml is left alone.

  2. Set the cadence and branch names

    Edit .github/sprint.yml. At minimum, set cadence.anchor to a date one of your sprints started and branches.base to whatever you cut sprints from.

  3. Check it reads the way you expect

    terminal
    PYTHONPATH=scripts python -m sprint validate

{
  "start_weekday": "thursday",
  "length_days": 14,
  "current_sprint": "Sprint_Q3_S5_082726_090926",
  "sprint_start": "2026-08-27", "sprint_end": "2026-09-09"
}

    If that isn’t the sprint you’re in, fix the anchor before going further.

  4. Add a SPRINT_TOKEN secret

    A fine-grained token with contents and pull requests read/write, stored as SPRINT_TOKEN. Without it the workflows fall back to GITHUB_TOKEN, and pull requests opened that way never trigger status checks — leaving nothing for a promotion to gate on.

  5. Protect the branches

    Protect base, the three env/* branches and release/*, so a reviewed pull request is the only way between environments. The automation assumes this and does not configure it. Without protection the gates are convention, not enforcement.

  6. Dry-run it

    Commit, then run Sprint – cut branch manually with force ticked. That cuts the branch on a non-sprint-start day so you can watch it work, then delete the branch if you like.

Set your cadence

Two values describe the whole schedule. There is no separate “which day” setting — the anchor is the day.

.github/sprint.yml
cadence:
  anchor: 2024-06-06          # a Thursday, so sprints start Thursdays
  length_days: 14             # so each one ends 13 days later, on a Wednesday
  start_weekday: thursday    # optional guard, must match the anchor
  timezone: America/Chicago  # the day your team recognises, not UTC
  numbering: quarter         # or: continuous
  start_number: 1            # what to call the sprint at the anchor
  fiscal_year_start_month: 1 # month your Q1 counts from

That is the anchor behind every branch name on this page. From 2024-06-06 to 27 Aug 2026 is 812 days, which divides exactly by 14 — so that Thursday starts a sprint, and it ends 13 days later on 9 Sep, giving Sprint_Q3_S5_082726_090926. Move the anchor to a Monday and every boundary moves with it, dates in the name included.

The guard

start_weekday is optional and exists only to catch a half-finished edit. Move the anchor without updating it and the config is rejected with the reason, rather than quietly cutting branches on the wrong day:

rejected
sprint: cadence.start_weekday says 'friday' but cadence.anchor
(2026-01-05) is a monday. Move the anchor to the friday you
want sprints to start on.

Joining part-way through an existing scheme

Nobody wants their sprint counter reset to 1 because they installed a tool. start_number says what to call the sprint that starts on the anchor — set it once and counting carries on.

already on sprint 23
cadence:
  numbering: continuous
  start_number: 23     # anchor sprint is S23, then S24, S25, ...

Under numbering: quarter it labels the anchor’s own quarter, and later quarters restart at 1 as usual — otherwise every quarter forever would open at start_number.

Worked example. Your team runs Monday fortnights and has just finished Sprint 23. The next one starts Monday 7 September 2026 and should be Sprint 24. Point the anchor at that date and name it:

.github/sprint.yml
cadence:
  anchor: 2026-09-07       # the next sprint's start date, a Monday
  length_days: 14
  numbering: continuous
  start_number: 24         # ...and it is Sprint 24

Point the anchor at the sprint you are naming

It does not have to be the first sprint you ever ran. Any date on the cycle works — earlier sprints simply extrapolate backwards from it. Pick the one whose number you are certain of.

Quarters that don’t open in January

fiscal_year_start_month is the month Q1 counts from. Leave it at 1 for ordinary calendar quarters. A firm whose financial year opens in April sets 4, and then July — calendar Q3 — is reported as Q2.

Both are set once and stay right indefinitely. A sprint straddling a quarter boundary keeps the quarter it started in.

Branch names

numbering: quarter resets the sprint number each quarter and gives Sprint_Q3_S5_082726_090926. numbering: continuous counts from the anchor and never resets: Sprint_S59_082726_090926. Release branches mirror whichever you pick.

Branch names your team recognises

A name nobody recognises is a name nobody trusts. Put your board code in it.

Out of the box you get the historical format. Add a naming section and the name is entirely yours:

.github/sprint.yml
naming:
  project_code: PROTS         # each team sets its own
  end_boundary: exclusive     # 8/13-8/27 shares its boundary with the next sprint
  sprint_template: "Q{quarter}_S{number}_{year}_{code}_{start:%m%d}-{end:%m%d}"
  release_template: "release/{sprint}"
Sprint startsBranchRelease branch
2026-08-13Q3_S4_2026_PROTS_0813-0827release/Q3_S4_2026_PROTS_0813-0827
2026-08-27Q3_S5_2026_PROTS_0827-0910release/Q3_S5_2026_PROTS_0827-0910
2026-10-08Q4_S1_2026_PROTS_1008-1022release/Q4_S1_2026_PROTS_1008-1022

The fields

quarter, number, year, code, index, start, end. Dates take strftime, so {start:%m%d} gives 0813 and {start:%Y-%m-%d} gives 2026-08-13. release_template also gets {sprint}, the sprint branch just built.

end_boundary changes the date, not the formatting

inclusive ends on the sprint’s own last day (8/26). exclusive ends on the next sprint’s start (8/27) — how most teams write a range, because the boundary is shared.

Every rendered name is checked against git’s ref rules before use, so a template producing a space or .. is rejected with an explanation rather than pushed. A single / is allowed — env/dit and release/ depend on it — but it nests the branch, worth knowing before putting 8/13 in a template.

Leave the naming section out and nothing changes: existing repos keep cutting Sprint_Q3_S5_082726_090926.

Self-hosted runners

Many organisations do not permit GitHub-hosted cloud runners. The workflows assume yours are self-hosted.

every sprint workflow
runs-on: ${{ vars.SPRINT_RUNNER || 'self-hosted' }}

Set a repository or organisation variable SPRINT_RUNNER to override it — ubuntu-latest where cloud runners are allowed, or a label like sprint-linux to pin a pool. No file edits, so every repo keeps an identical payload.

What your runners need

RequirementNeeded by

Each workflow runs a preflight that names anything missing rather than failing obscurely three steps later. actions/setup-python is marked continue-on-error and pip install falls back to whatever is already installed — so a runner with no route to PyPI still works, provided Python and PyYAML are pre-installed on the image.

Day to day

Four workflows. Three run daily and self-gate, so on most days they run and deliberately do nothing.

WorkflowRunsWhat it does
Sprint – cut branch daily, or manual On a sprint start day, cuts the sprint branch from your base branch.
Sprint – promote daily, or manual On the sprint’s last day, opens the sprint → DIT pull request. Run it by hand for any later hop.
Sprint – back-merge daily, or manual Opens a pull request whenever UAT or a release branch has drifted ahead of your base branch.
Sprint – validate config on pull requests Checks sprint.yml and runs the cadence tests before a bad edit can land.

Every promotion step is safe to re-run. A branch that already exists, a pull request already open, or a head branch with nothing new to give are each reported and skipped — never duplicated, never a red build.

Promoting through environments

Run the promote workflow and pick the hop.

In the repo’s Actions tab, choose Sprint – promote, then Run workflow, and select the hop:

  • dit — sprint branch into env/dit. Usually already opened for you at sprint end.
  • sit — env/dit into env/sit, once DIT checks out.
  • uat — env/sit into env/uat, once SIT checks out.
  • release — cuts release/<sprint> from env/uat. No pull request; the branch simply appears.

Each of the first three opens a pull request. Review it, let the checks run, merge it. Merging is what moves the code — the workflow only ever proposes.

The first time you promote in a repo, an env/* branch that doesn’t exist yet is seeded from your base branch so the promotion has somewhere to land.

Promoting a sprint other than the current one? Pass any date inside it as sprint_date.

Back-merge, and why it matters

This is the one habit that keeps the model honest.

Branch-per-environment drifts. A hotfix applied to env/uat or to a release branch exists only there. The next sprint gets cut from a base branch that never received it, and the fix quietly disappears from production.

Merge these promptly

The back-merge workflow opens a pull request the moment UAT or a release branch runs ahead of your base branch. Letting those sit is how this model fails — silently, a sprint or two later, in production.

It runs on a schedule rather than on a push, so it keeps working no matter what you rename your branches to. Turn it off with promotion.backmerge_to_base: false only if you have another mechanism for the same problem.

Rolling out updates

The payload is copied, so improvements need pushing out. The installer makes that one command per repo instead of a hand-edit per repo.

terminal
# Which repos have fallen behind?
./tools/install.sh --check /path/to/repo

template version:  1.0.0
installed version: 1.0.0
  DIFFERS  .github/workflows/sprint-cut.yml
  config   .github/sprint.yml present (never overwritten)

# Bring one up to date. Your sprint.yml is never touched.
./tools/install.sh /path/to/repo

--check changes nothing, so it is safe to run across every repo you own. Cadence lives in sprint.yml, which the installer always preserves — an update can never reset a team’s schedule.

When it breaks

The failures you are most likely to hit first.

SymptomCause and fix
“base branch develop does not exist”, daily The repo doesn’t have the branch named in branches.base. Point it at the branch you really cut from, or create it.
Promotion PR sits with no checks It was opened with GITHUB_TOKEN. Add the SPRINT_TOKEN secret; PRs opened by the default token never trigger workflows.
No branch cut this morning Most likely correct — it only cuts on sprint start days. Confirm with python -m sprint status, which prints the current window.
“head branch does not exist” on promote Promoting a sprint whose branch was never cut. Run the cut workflow, or pass a sprint_date inside the sprint you meant.
Merge conflict on a promotion Expected, and it surfaces in the pull request like any other. Resolve it there; the workflow proposes, it never force-merges.
Wrong sprint number or dates Almost always the anchor. Run python -m sprint validate and check the window it prints against the sprint you are actually in.

Inspecting without touching anything

terminal
export PYTHONPATH=scripts

python -m sprint status                    # where today falls
python -m sprint status --date 2026-09-10  # any date, past or future
python -m sprint promotion --hop dit       # what the next PR would say
pytest tests -q                            # the cadence tests

None of these touch git or GitHub. They only compute, so they are safe to run anywhere, any time.
